# livesim-content

This repo contains test content used by the DASH-IF online
service [livesim2][livesim2]. You can also generate your own
test content locally, see [Generate your own assets](#generate-your-own-assets).

For easy download, a mixed storage format is used
where each representation
directory with hundreds of files is made into an archive
(in zip format) while top-level files are kept separated.

This allows for simple changes to the MPDs, while making
the downloads more efficient. Since github has a file size
limit of 100MB, [git-lfs][git-lfs] is used.

There are also metadata files for each representation to
allow for boosted startup of livesim2, like
`testpic_2s/V300_data.json.gz`.
By reading these files, livesim2 has the knowledge about
the duration of each segment and does not need to
scan all the segments at startup.
These reduces the startup time for livesim2 when run
with all the content of this repo substantially
goint from minutes to seconds.

The repdata files are generated by running livesim2 with
the option `--writerepdata`.

## Download assets

To download the assets, you need [git-lfs][git-lfs] installed.

On Linux, use your package manager to install it like:

```sh
> apt install git-lfs
```

On Mac, you can analogously run

```sh
> brew install git-lfs
```

After that, set up git-lfs once for your user account and clone the repo:

```sh
> git lfs install
> git clone https://github.com/Dash-Industry-Forum/livesim-content.git
```

If the `.zip` files in the clone are small text files (LFS pointers) instead of
archives, the LFS content was not downloaded. Fetch it from inside the repo with

```sh
> git lfs pull
```

The Git LFS downloads count against a limited monthly budget of the DASH-IF
organization. If it is used up, the clone has only pointer files and
`git lfs pull` fails with "This repository exceeded its LFS budget".
Then try again next month, or open an issue.

To save bandwidth, you can fetch only the assets you need, e.g.

```sh
> GIT_LFS_SKIP_SMUDGE=1 git clone https://github.com/Dash-Industry-Forum/livesim-content.git
> cd livesim-content
> git lfs pull --include "testpic_2s/*"
```

### Unpacking the content

You finally need to unpack the content.

All content can be unzipped using the top-level command

```sh
> unpack_all.sh
```

that finds the zip files at any depth and unzips each one in its own directory.
It then runs the `postunpack.sh` script of any asset that has one, which
makes files that are not stored in the repo, like the fixed MPD of
`mpeg-h_one-day-in-berlin`. `testpic4_8s` and `testrotate_2s` have no zip
files; they are generated, as described in their sections.

You can also unpack a single asset like `testpic_2s` using

```sh
> cd testpic_2s
> ../tools/unpack.sh
```

to unpack all the zip-files and run the asset's `postunpack.sh`, if any.
Where the representations are in a subdirectory, run it there, e.g. in
`ads/train_ad`.
If you want to remove the `.zip` files, run `tools/unpack_and_clean.sh` instead.

You can remove the zip-files, but it may be good to keep them so that an update
via git only downloads new assets. After a git update, check if any zip-file has
been updated and run the unpack tool on that specific directory.

The asset should now be in a format that can be read and processed by `livesim2`,
provided that it is in a subdirectory under `--vodroot`.

## Generate your own assets

Instead of downloading assets, you can generate test assets locally with
[`tools/contentgen`](tools/contentgen/README.md), at any duration, from a small
YAML config. It needs Go and an ffmpeg with the encoders used (Homebrew's
`ffmpeg-full` has all of them). It supports:

* AVC, HEVC and AV1 video, optionally with B-frames (with negative
  composition time offsets, so that the presentation starts at 0)
* AAC, Opus and AC-3 audio, with the encoder priming handled
* multi-bitrate content: video and audio representations that share an
  Adaptation Set, so that a player can switch between them
* extra MPDs with some of the representations, and GOPs shorter than the
  segments
* integer frame rates and 29.97, 59.94 and 23.976 fps
* `$Number$` with `@duration`, SegmentTimeline with `$Time$`, and
  SegmentTimeline with `$Number$` (which livesim2 does not read yet,
  [livesim2 #152](https://github.com/Dash-Industry-Forum/livesim2/issues/152))

The video is the ffmpeg `testsrc2` pattern, complex enough that the encoders
use their bitrate. On it are burned-in labels (codec, bitrate, resolution,
frame rate, representation, segment and frame number), a large timecode, the
DASH-IF logotype, and a white square that flashes at every second together
with a beep in the audio. The `@bandwidth` values are computed from the
segments.

These example configs are in [`tools/contentgen/examples`](tools/contentgen/examples).
They are about two minutes long, and `-duration` sets another length:

| Config | Content |
| ------ | ------- |
| `ladder_2s.yaml` | AVC at 400, 800 and 1600 kbps (360p to 720p), AAC at 64 and 128 kbps, 2 s segments |
| `two_languages_2s.yaml` | English audio with a monotonic beep (main) and Swedish audio with rising tones, in separate Adaptation Sets |
| `codecs_2s.yaml` | AVC, HEVC and AV1 ladders, and AAC, Opus and AC-3, with SegmentTimeline and `$Time$` |
| `bframes_2s.yaml` | AVC and HEVC with B-frames at 30 fps, and AAC with its priming in an edit list |
| `timeline_number_2s.yaml` | SegmentTimeline with `$Number$` |
| `ntsc_2s.yaml` | 29.97 fps with 2.002 s segments and a drop-frame timecode |
| `ntsc60_2s.yaml` | 59.94 fps with 2.002 s segments |

To generate an asset and serve it with livesim2:

```sh
> go -C tools/contentgen build
> mkdir -p ~/vod/myasset
> cp tools/contentgen/examples/ladder_2s.yaml ~/vod/myasset/contentgen.yaml
> FFMPEG=/opt/homebrew/opt/ffmpeg-full/bin/ffmpeg tools/contentgen/contentgen -config ~/vod/myasset/contentgen.yaml
> livesim2 --vodroot ~/vod
```

The asset is then at `http://localhost:8888/livesim2/myasset/Manifest.mpd`.
At 29.97 and 59.94 fps, durations that loop seamlessly are not whole seconds;
`contentgen -config <config> -suggest 3600` lists the ones near an hour.

## Assets

The assets available are:

### ads

Five 10s ads for the server-guided ad insertion (SGAI) of livesim2, each
with its own `manifest.mpd`. They are made from the repo maintainer's own
video recordings, and some have AI-generated elements. Nothing is copied from
other sources.

Each ad has 30fps AVC video at 1280x720 (V4, about 4 Mbps), 960x540 (V2,
about 2 Mbps) and 640x360 (V1, about 1 Mbps), and AAC audio (A, about
97 kbps), with 2s segments. `ads/ads.json` gives each ad a title and the
interests that livesim2 uses to choose ads.

| Directory | Title |
| --------- | ----- |
| ads/train_ad | Train Journey |
| ads/namibia_ad | Namibia |
| ads/namibia_safari_ad | Namibia Safari |
| ads/gotland_runt_ad | Gotland Runt Sailing Race |
| ads/stockholm_sailing_ad | Sailing in Stockholm |

### dolby-ac4

One 2.002s segment of 1080p AVC video at 29.97fps with AC-4 5.1 audio, in
`dolby-ac4/2997fps`. It is based on the Dolby DASH-IF test vector
`Living_Room_1080p_20_96k_2997fps`, with the segment adjusted because the
original was not fully correct. livesim2 has the same segments in its test
assets.

### mpeg-h_one-day-in-berlin

The "One Day in Berlin" MPEG-H Audio demo, 1:57 long with 1.92s segments.
The video is HEVC Main 10 at 1920x1080, 50fps (about 9.6 Mbps), and the audio
is MPEG-H 3D Audio (`mhm1`, about 960 kbps) with three Preselections.

This is a custom version that [Fraunhofer IIS](https://www.iis.fraunhofer.de/en/ff/amm/broadcast-streaming/mpegh.html)
made for use in livesim2. The original demo and more MPEG-H test material are at
[mpegh.com](https://mpegh.com/academy/testing-and-qa/).
Copyright (c) 2023 Fraunhofer-Gesellschaft zur Förderung der angewandten
Forschung e.V., licensed under
[CC BY-NC-ND 4.0](https://creativecommons.org/licenses/by-nc-nd/4.0/).

The segments are not in Representation subdirectories, so each zip file
unpacks into the asset directory itself.

The repo has the MPD as Fraunhofer IIS made it, in `manifest.mpd.orig`. In it,
the `AudioChannelConfiguration` of the audio Adaptation Set comes after the
`SegmentTemplate`, which the DASH schema does not allow. When unpacking,
`postunpack.sh` writes `manifest.mpd` with that element moved, so run
`unpack_all.sh` or `tools/unpack.sh` to get the MPD.

A 1-hour long asset with 2s segments with 30fps video and many subtitle options.

The MPDs that can be played live are:

| Manifest_dvb.mpd | same as Manifest.mpd, but adding DVB profiles | OK |
| Manifest_stpp.mpd | Manifest.mpd extended with stpp subtitles | OK |
| Manifest_thumbs.mpd | Manifest.mpd extended with DASH-IF image subtitle track | OK |
| Manifest_trickmode.mpd | Manifest.mpd extended with DASH trick mode track | OK |
| audio.mpd | audio only | OK |
| cea608.mpd | video includes two CEA-608 caption tracks | OK |
| cea608_and_segs.mpd | same as cea608.mpd extended with stpp subtitle track | OK |
| multi_subs.mpd | Manifest.mpd extended with 5 subtitle and caption tracks in stpp format | OK |
| stpp_one_region.mpd | Manifest.mpd extended with `S1_one_region` stpp subtitles | OK |
| stpp_two_regions.mpd | Manifest.mpd extended with `S1_two_regions` stpp subtitles | OK |
| stpp_two_regions_multi_color.mpd | Manifest.mpd extended with `S1_two_regions_multi_colors` stpp subtitles | OK |

In addition, there is a couple of MPDs that can only be played as VoD because of side-loaded subtitle files or too short
subtitle track.

| Name | Specifics  | livesim2 status |
| ---- | ---------- | --------------- | 
| img_subs.mpd | Manifest.mpd extended with image subtitles in side-loaded TTML format (not supported by livesim) | N/A |

The side-loaded subtitle MPDs (`img_subs.mpd`, `ttml_subs.mpd` and
`webvtt_subs.mpd`) signal the full profile, since their subtitles are single
files without a `SegmentTemplate`, which the live profile does not allow. Their
subtitle Representations have no `@codecs`, since `@mimeType`
(`application/ttml+xml` or `text/vtt`) identifies them, as in DASH-IF IOP 4.3
6.4.5.

Known issues:

* `Manifest_dvb.mpd` uses `avc1` sample entries, while DVB-DASH recommends
  `avc3`. The V300 segments already carry their parameter sets in-band, so the
  livesim2 URL option `inbandps_1` gives `avc3`, as in
  `https://livesim2.dashif.org/livesim2/inbandps_1/testpic_2s/Manifest_dvb.mpd`.

### testpic_2s_av1

A 10s asset with 2s segments for AV1. The video is AV1 at 1280x720, 25fps,
at 400 kbps (`av1`) and 600 kbps (`av1_600`). The audio (`A48`) is AAC at
128 kbps with a C-major scale, one note per second, and the encoder priming
removed. The content was made with the tools in
[moqlivemock](https://github.com/Eyevinn/moqlivemock) (`utils/contentgen`):
the ffmpeg `testsrc` pattern with a rotating logo and the codec, bitrate,
resolution, time and frame number.

The AV1 representations use 2-4% more than their `@bandwidth`.

### testpic_2s_low_delay

An 8s asset with 2s segments, added together with the L3D-DASH (low-delay)
support of livesim2.
The video is the ffmpeg SMPTE HD color bars with the resolution, a timecode
and the bitrate, in AVC at 30fps with B-frames. Two Adaptation Sets have the
same ladder at 1920x1080, 1280x720 and 640x360: `1080`, `720` and `360` have
a 2s GOP, and `LD_1080`, `LD_720` and `LD_360` ("Low Delay" in the picture)
a GOP of 6 frames (0.2s). The audio (`A48` and `LD_A48`) is the first 8s of
the `testpic_2s` audio.

Known issues:

* The audio has the 1024 samples of AAC priming of `testpic_2s/A48`, but no
  edit list. testpic_2s got one in v2.0.0. It is left out here until
  livesim2.dashif.org runs a livesim2 version that handles audio edit lists in
  all modes.
* The color bars are easy to encode, so the 2s-GOP representations use only
  about a third of their `@bandwidth` (`1080` uses 681 kbps of 2000 kbps). The
  audio uses about 53 kbps, more than its `@bandwidth` of 48 kbps.

### testpic4_8s

A 1-hour asset with 8s segments, with 30fps video at three bitrates and MPDs
that contain different subsets. Only its config, `testpic4_8s/contentgen.yaml`,
is stored in the repo. [`tools/contentgen`](tools/contentgen/README.md) generates
the content, with the look described in
[Generate your own assets](#generate-your-own-assets):

```sh
> go -C tools/contentgen build
> FFMPEG=/opt/homebrew/opt/ffmpeg-full/bin/ffmpeg tools/contentgen/contentgen -config testpic4_8s/contentgen.yaml
```

This takes about 6 minutes on a recent Mac and writes about 930 MB. If the
directory still has the stored content of v2.1.0 or earlier, add `-force`,
since contentgen only replaces what it made itself.

The video is AVC at 30fps with closed 1s GOPs and 3 B-frames. The audio is
AAC-LC, 48kHz stereo, with a beep every second.

| Rep | Type | Details |
| --- | ---- | ------- |
| V300 | video | 640x360, 300 kbps |
| V600 | video | 640x360, 600 kbps |
| V1200 | video | 960x540, 1200 kbps |
| A48 | audio | 48 kbps, lang `en` |

The MPDs are:

| Name | Specifics  | livesim2 status |
| ---- | ---------- | --------------- |
| Manifest.mpd | SegmentTemplate with `$Number$` and all bitrates | OK |
| Manifest300.mpd | same as Manifest.mpd but limited to 300kbps video | OK |
| Manifest600.mpd | same as Manifest.mpd but limited to 300kbps and 600kbps video | OK |

### testrotate_2s

A 1-hour asset with 2s segments, based on the test content of
[moqlivemock](https://github.com/Eyevinn/moqlivemock) (`utils/contentgen`).
Unlike the other assets, the media is not stored in the repo. Only the
generator is: `testrotate_2s/gen.sh`, the Go tool `audioseg` and the fonts
and logo in `resources`. Run the generator to make the content locally.

The video is the ffmpeg `testsrc` pattern with a logo that turns once every
10 s. On it are the bitrate, the resolution, the frame number and a large
`MM:SS;FF` timecode. The video is AVC at 25fps with a closed 2s GOP and no
B-frames. The audio is two AAC-LC tracks (64 kbps CBR, 48kHz stereo). The
encoder priming is removed, so there is no edit list, and every audio segment
starts with the first AAC frame at or after the video segment start.

| Rep | Type | Details |
| --- | ---- | ------- |
| V1200 | video | 1280x720, 1200 kbps (orange text) |
| V800 | video | 960x540, 800 kbps (yellow text) |
| V400 | video | 640x360, 400 kbps (white text) |
| Amon | audio | 880 Hz beep every second (lang `mon`) |
| Asca | audio | C-major scale, one note per second (lang `sca`) |

The generator also writes the only MPD, `Manifest.mpd`.

`gen.sh` needs Go, [`mp4ff-pslister`][mp4ff] on the `PATH`, an ffmpeg with
`libx264` and `drawtext`, and an ffmpeg with `libfdk_aac`. Few builds have
both, so the two can be set separately (default: `ffmpeg` on the `PATH`):

```sh
> cd testrotate_2s
> FFMPEG=/opt/homebrew/opt/ffmpeg-full/bin/ffmpeg FFMPEG_AAC=/path/to/ffmpeg-with-libfdk_aac ./gen.sh
```

The default duration is 3600 s; give another one in seconds, e.g.
`./gen.sh 120`. Use a multiple of 8 s, so that the audio is a whole number of
AAC frames (8 s is 375 frames at 48kHz). `gen.sh` replaces the representation
directories and `Manifest.mpd` of an earlier run.

## Tools

### check_assets.sh

`tools/check_assets.sh` checks the MPDs of all unpacked assets and all their
segments with [dashcheck][dashcheck]. It compares the errors and warnings with
the known ones in `tools/check_assets_known.txt`, which are documented under
[Assets](#assets). It exits with 1 if there are new findings, and lists known
findings that are gone. Run it by hand after changing content; a CI job would
download all the LFS content on every run. The known findings are those of
dashcheck v0.3.0.

```sh
> go install github.com/tobbee/dashcheck/cmd/dashcheck@latest
> ./unpack_all.sh
> tools/check_assets.sh
```

It takes about 20 s for all assets. `testpic4_8s` and `testrotate_2s` are only
checked when they have been generated. After fixing or accepting findings,
`tools/check_assets.sh -update` writes the current findings to the known list.

### contentgen

`tools/contentgen` generates test assets from a YAML config, as described in
[Generate your own assets](#generate-your-own-assets). See its
[README](tools/contentgen/README.md) for the config, the options and the
timing details.

### elstpatch

`tools/elstpatch` is a Go tool (based on [mp4ff][mp4ff]) that checks where the
presentation of a representation starts. It can then fix the start by adding a
single-entry CMAF edit list (`elst`) to the init segment. The media segments
are never changed.

* video: the first picture often has a composition time offset because of
  B-frames. The edit list removes that offset so the first picture is
  presented at time 0.
* audio: the edit list removes the AAC encoder priming (`-priming`, in audio
  samples), so it is not played. The priming can't be seen in the segments,
  and may already have been removed when the asset was made. Measure it, e.g.
  by decoding, before giving it. Without `-priming`, audio is left alone.

Without `-write`, the tool only reports. For each init segment it prints the
existing edit list, segment count, total duration, and the offset between
earliest presentation time and `tfdt` in all segments. The edit list shifts
every segment by the same amount, so for video that offset should be the same
in every segment. Each argument is a representation directory with
`init.mp4` and `*.m4s` segments. Writing is refused if mp4ff can't
re-encode the original `init.mp4` byte for byte.

```sh
> go -C tools/elstpatch build
> tools/elstpatch/elstpatch testpic_2s/V300 testpic_2s/A48    # report only
> tools/elstpatch/elstpatch -write -priming 1024 testpic_2s/V300 testpic_2s/A48
```

livesim2 reads the edit list from the init segment. For audio it shifts the
SegmentTimeline times (`$Time$`) by the priming, and shortens the first segment
of the timeline. After patching, update the `init.mp4` entry in the
representation `.zip` file (e.g. `cd testpic_2s && zip V300.zip V300/init.mp4`),
and regenerate the representation data with `livesim2 --writerepdata`.
